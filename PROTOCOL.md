# FireCast Wire Protocol — v1

**Status:** Draft v1 · **Transport:** JSON over WebSocket · **Scope:** Receiver-agnostic

One phone sender app must drive two receivers with zero protocol changes:

- **Vega OS receiver** — Amazon Appstore app for Fire TV Stick 4K Select / 3rd-gen 4K (React Native + native player module)
- **Fire OS receiver** — sideloadable APK for Fire OS sticks (ExoPlayer)

Everything below is transport + message semantics. Nothing here is Android-, Vega-, or player-specific.

---

## 1. Discovery

Receivers MUST be discoverable by at least one of these mechanisms. Senders MUST try them in order and MUST offer manual IP/hostname entry as a fallback.

### 1a. DIAL (preferred on Fire TV)

Standard [DIAL 2.x](http://www.dial-multiscreen.org/) discovery and launch.

1. Sender multicasts SSDP `M-SEARCH` to `239.255.255.250:1900`:

   ```
   M-SEARCH * HTTP/1.1
   HOST: 239.255.255.250:1900
   MAN: "ns=01"; ns=01
   ST: urn:dial-multiscreen-org:service:dial:1
   MX: 3
   ```

2. Receivers reply with `LOCATION:` pointing at their DIAL device-description XML.
3. Sender `GET`s the description, reads the `Application-URL` header/base.
4. Sender `GET`s `{Application-URL}/FireCast` to read receiver state (`<state>running|stopped|installable=...`).
5. To launch, sender `POST`s to `{Application-URL}/FireCast` with `Content-Type: text/plain` and an optional launch payload (the receiver's WebSocket URL is returned in the `Location` header / `201 Created`, or the sender falls back to 1b/1c to find the control channel).
6. To stop, sender `DELETE`s `{Application-URL}/FireCast/run`.

The registered DIAL application name is **`FireCast`**.

### 1b. mDNS (fallback / non-DIAL receivers)

Receiver advertises `_firecast._tcp.local` with TXT records:

| Key       | Value                                              |
|-----------|----------------------------------------------------|
| `v`       | Protocol version, e.g. `1`                         |
| `name`    | Human-readable device name, e.g. `Living Room TV`  |
| `ws`      | WebSocket control path, e.g. `/firecast`           |
| `dial_id` | `FireCast` (if DIAL is also supported)             |

The WebSocket URL is `ws://<resolved-host>:<port><ws-path>`.

### 1c. Manual entry

Sender MUST allow typing an IP address or hostname plus port, then attempt the WebSocket handshake directly (`ws://host:port/firecast`).

## 2. Pairing / confirmation (first connect)

To prevent a neighbor on the same LAN from hijacking the TV, the first connection from an unknown sender MUST be confirmed:

1. Sender opens the WebSocket and sends `hello` (see §4).
2. Receiver replies `hello_result` with `"paired": false` and shows a 4-digit PIN on the TV screen.
3. Sender prompts the user for the PIN and sends `pair`.
4. Receiver replies `pair_result`. On success, the sender's fingerprint (random UUID generated by the sender, sent in `hello`) is remembered; later connections with the same fingerprint skip the PIN.

Receivers MAY additionally offer "always allow on this network" — out of scope for v1.

---

## 3. Message envelope

Every frame is a single UTF-8 JSON object, one per WebSocket text message:

```json
{
  "v": 1,
  "id": "3f9a…",          // client-generated UUID; every command gets one
  "type": "<command>",    // e.g. "play"
  "payload": { }          // command-specific, may be {}
}
```

Responses echo the command's `id`:

```json
{
  "v": 1,
  "id": "3f9a…",
  "type": "play_result",
  "payload": { "ok": true }
}
```

Unsolicited receiver events have **no** `id`:

```json
{ "v": 1, "type": "status", "payload": { "state": "playing", "position": 42.5 } }
```

Rules:

- Unknown `type` values MUST be ignored (forward compatibility).
- `payload` fields not understood MUST be ignored.
- Receivers MUST reply to every command with `<type>_result` and `{"ok": true|false, "error"?: "..."}`.
- All times are **seconds** (float). All volumes are **0.0–1.0** (float).

## 4. Commands (sender → receiver)

### `hello`
```json
{ "v": 1, "id": "…", "type": "hello",
  "payload": { "client": "FireCast Android", "client_version": "0.1.0",
               "fingerprint": "<uuid>", "protocol": 1 } }
```
→ `hello_result`: `{ "ok": true, "paired": true|false, "receiver": "FireCast Vega", "receiver_version": "0.1.0", "protocol": 1 }`.
If `protocol` mismatches, receiver replies `ok: false, error: "protocol_mismatch"`.

### `pair`
```json
{ "v": 1, "id": "…", "type": "pair", "payload": { "pin": "4821" } }
```
→ `pair_result`: `{ "ok": true }` or `{ "ok": false, "error": "bad_pin" }`.

### `play`
```json
{ "v": 1, "id": "…", "type": "play",
  "payload": { "url": "http://192.168.1.5:8080/media/a1b2c3.mp4",
               "title": "My Vacation.mp4", "mime": "video/mp4",
               "position": 0.0,
               "headers": { "Authorization": "…" } } }
```
`title`, `mime`, `position`, `headers` are optional. `headers` lets the sender pass auth for private URLs. Receiver MUST stop any current playback first.
→ `play_result`: `{ "ok": true }` or `{ "ok": false, "error": "unplayable" }`.

### `pause` / `resume` / `stop`
Empty payload. → `<type>_result` with `ok`.

### `seek`
```json
{ "v": 1, "id": "…", "type": "seek", "payload": { "position": 95.5 } }
```

### `volume`
```json
{ "v": 1, "id": "…", "type": "volume", "payload": { "level": 0.7 } }
```

### `mute`
```json
{ "v": 1, "id": "…", "type": "mute", "payload": { "muted": true } }
```

### `get_status`
Empty payload. → `get_status_result` whose payload is the full status object (§5).

---

## 5. Events (receiver → sender, no `id`)

### `status` — full state snapshot (sent on every state change and in reply to `get_status`)
```json
{ "v": 1, "type": "status",
  "payload": { "state": "playing", "position": 42.5, "duration": 3600.0,
               "volume": 0.7, "muted": false, "title": "My Vacation.mp4" } }
```
`state`: `idle | loading | playing | paused | buffering | ended | error`.
`duration` may be `-1` for live/unknown.

### `position` — throttled progress (receiver SHOULD emit ~1/sec while playing)
```json
{ "v": 1, "type": "position", "payload": { "position": 43.5, "duration": 3600.0 } }
```

### `ended`
```json
{ "v": 1, "type": "ended", "payload": {} }
```

### `error`
```json
{ "v": 1, "type": "error", "payload": { "code": "fetch_failed", "message": "HTTP 404 from media URL" } }
```
Suggested codes: `fetch_failed`, `unsupported_mime`, `decode_error`, `network_lost`.

---

## 6. Keepalive

Either side MAY send `{ "v": 1, "type": "ping" }` (no `id`); the other MUST reply `{ "v": 1, "type": "pong" }`.
Senders SHOULD ping every 30 s of inactivity and treat two missed pongs as a dead connection.

---

## 7. LAN HTTP media serving (local files)

The phone cannot hand the receiver a `file://` path — the receiver is a different machine. Convention for local files:

1. The sender runs an embedded HTTP server on the LAN interface (default port `8080`, configurable).
2. Each shared file gets a random, unguessable token path: `http://<phone-lan-ip>:8080/media/<token>` where `<token>` is ≥128-bit hex, valid for the session only.
3. The server MUST:
   - send a correct `Content-Type` (from file extension / sniffed bytes),
   - support `Range` requests (`Accept-Ranges: bytes`, `206 Partial Content`) — receivers seek by range-requesting,
   - send `Content-Length`,
   - bind all interfaces but serve **only** the token paths (no directory listing).
4. The sender puts that URL in `play.url` with the matching `mime`.
5. Remote (http/https) URLs are passed through untouched — no proxying.

Receivers fetch the URL like any HTTP media source. This is the same pattern DLNA/BubbleUPnP uses and works with ExoPlayer, AVPlayer, and HTML5 `<video>` alike.

---

## 8. Versioning

- `v` is the protocol major version. v1 receivers MUST reject (`protocol_mismatch`) unknown majors.
- Minor additions MUST be optional fields / new `type`s only — never change existing field meanings.
- The DIAL application name `FireCast` and mDNS service `_firecast._tcp` are version-independent; version negotiation happens in `hello`.

## 9. Minimal session example

```
S → R  M-SEARCH  (SSDP)
R → S  200 OK, LOCATION: http://192.168.1.10:8060/dd.xml
S → R  GET /dd.xml  →  Application-URL: http://192.168.1.10:8060/apps
S → R  POST /apps/FireCast  →  201 Created
S → R  WS ws://192.168.1.10:8090/firecast
S → R  {"v":1,"id":"1","type":"hello","payload":{"client":"FireCast Android","fingerprint":"…"}}
R → S  {"v":1,"id":"1","type":"hello_result","payload":{"ok":true,"paired":false,…}}
        (TV shows PIN 4821)
S → R  {"v":1,"id":"2","type":"pair","payload":{"pin":"4821"}}
R → S  {"v":1,"id":"2","type":"pair_result","payload":{"ok":true}}
S → R  {"v":1,"id":"3","type":"play","payload":{"url":"http://192.168.1.5:8080/media/a1b2","title":"Clip.mp4","mime":"video/mp4"}}
R → S  {"v":1,"id":"3","type":"play_result","payload":{"ok":true}}
R → S  {"v":1,"type":"status","payload":{"state":"playing","position":0.0,"duration":125.0,…}}
R → S  {"v":1,"type":"position","payload":{"position":1.0,"duration":125.0}}
…
S → R  {"v":1,"id":"4","type":"stop","payload":{}}
```

## 10. Security notes (v1)

- LAN-only by design; no cloud relay in v1.
- Per-session random tokens for served files; tokens expire when the sender app closes the session.
- PIN pairing on first connect; remembered fingerprints after.
- No DRM content in v1 (receivers play clear HTTP(S) media only).
